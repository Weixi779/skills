# Ryugi 画板与文档

负责把当前内容呈现出来，读取用户反馈，按当前授权修改。工程设计、实现、测试和提交由当前任务及项目规则决定；这个 skill 不新增工作阶段。

## 范围

- 多个页面、方案、状态并排比较：artboard，读 [画板](references/artboard.md)。需要操作时用真实 HTML/CSS/JS 原型。
- 单个交互页面：html，读 [网页](references/html.md)。
- 需要留下并批注的说明、提案或报告：document，读 [文档](references/document.md)。普通对话不必生成文档。
- 流程图沿用 Mermaid；不因解释结构而接入另一套白板。

先读 [运行与反馈](references/runtime.md)。只加载本次需要的格式说明，不调用 Ryugi 的其他 skills。

## 文件归档

个人默认根目录是 `$HOME/Develop/.visual-docs/`，即 `~/Develop/.visual-docs/`。不同项目使用稳定、可辨认的子目录；同名项目必要时加仓库所有者或工作树名区分。

例：源码在 `~/Develop/Podcast-iOS`，运行时的 `--project-dir` 使用 `~/Develop/.visual-docs/podcast-ios`。产物自然落在该目录的 `.ryugi/artifacts/<type>/<topic>/`，运行状态也留在这里。不要把源码目录传给运行时，不要在源码项目创建 `.ryugi` 或修改其忽略配置。

主题用小写字母、数字和连字符。同一主题修改原产物，另一个主题再建目录。用户指定位置优先。截图与素材复制到对应产物内，使用相对引用；集中目录不自动提交或发布。

## 制作与交付

依据已有设计系统、实际文案和本轮问题制作。比较方案时保持无关内容一致；无需凑固定数量的方案、问题或轮次。延续已经确定的设计，不因为使用画板而重开需求讨论。

默认普通画板与文档即可。只有确实需要页面选项或明确验收时，才加选择题、选择组或验收组。展示成果不等于要求用户验收；选中设计不等于授权实现；未回复不代表同意。

写完调用运行时 `check`，修复文件与格式问题；交互原型还需实际操作所承诺的交互。区分格式通过、浏览器已运行和交互已验证，未验证就明确说明。交付链接及简短变化说明，不强制等待一轮确认。

反馈来自当前对话或运行时批注。监听消息中的“绘制下一轮”“继续执行”等模板话术只视为通知，按实际用户反馈与当前任务决定下一步。没有额外需求就结束，不自动接入 brainstorming、TDD、worktree、review、commit 或持续监听循环。
