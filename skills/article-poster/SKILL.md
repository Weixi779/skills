# 文章 Poster

让每篇文章拥有自己的画面，同时适合当前网站的展示方式。统一视觉语言，不把不同文章套成同一张图。

## 先确定依据

- 读目标文章全文、frontmatter 与已有头图。用户只要求审阅时，不自动生成或替换；只有一篇任务时，不扩成全站补图。
- 优先读取项目明确指定的视觉规范；本站约定入口是 `docs/poster-art-direction.md`，接入细节见 `docs/banner-images.md`。在其他项目中没有这些文件时，依据该项目规范和当前用户要求，不套用另一站点的配色或主题。
- 接入前核对实际 Banner 组件、样式和内容 schema。原图比例、页面容器比例、手机裁切是三个不同问题，不能仅凭图片文件的长宽判断效果。
- 区分用户确认的要求、单篇决定、实现现状和建议。已有明确授权就继续，不把 skill 变成额外审批关卡；关键意象仍不明确时，只问会改变画面的那个问题。

## 从文章到画面

用一两句话概括“这篇文章值得留下的意象是什么”，并说明它来自哪段内容或哪个具体对象。情绪性解读是候选理解，不替作者宣称人生结论。涉及个人表达时遵循项目的作者资料和写作边界。

选择能承载这个意象的媒介：插画、静物、屏幕摄影感、抽象构成等，服从文章和站点规范。不要把标题里的所有关键词画一遍，也不要把所有技术文章都变成电脑、代码和节点图。

Poster 可以是概念图；真正承担解释责任的架构图、流程图、数据图则需要真实关系和可读标注，必要时采用 SVG 等可编辑形式。不要把生成的装饰性界面或连线当作文章事实。

审阅现有图时判断：直接保留、调整构图、重生成，或暂不需要封面。翻转只是可选手段；先检查文字、标志、方向性物体与语义，不把它当默认修复。

## 生成与定向修改

生成或编辑位图时使用当前环境的 `imagegen` 技能和内置图片生成工具。先查看本地参考图，明确它是风格参考、构图参考还是编辑目标。不要用 SVG 冒充应当生成的位图，也不要因内置工具不便就擅自切换 API 或模型。

把提示词组织为实际需要的几部分，不必每次套满模板：

> 用途与媒介 → 文章意象／主体 → 文字区和主体位置 → 构图、尺寸与裁切容错 → 色彩和光线 → 有意义的细节 → 本次必须避免的内容。

图片里的主体不要与页面标题竞争。按当前 Banner 的蒙层和裁切安排信息，而不是把页面蒙层或标题直接烘焙进图片。需要仿界面画面时，明确它是装饰性意象；需要精确文字则另行校验，不依赖生成结果猜测。

修改已选中的图时，保留已认可的主体、构图与气质，只改被指出的问题。若要日夜双图，以已选图为参考保留场景和物体关系，再调整光线或界面明暗；是否需要双图由题材与实际展示决定，不自动翻倍生成。

## 放进页面再判断

先看原图，再用真实标题、摘要和当前蒙层验证页面效果：

- 桌面浅色／深色是否读得清标题，同时看得出主体。
- 手机是否切掉了关键物体；长标题和摘要自然换行后，画面是否仍成立。
- 显示单图或双图时，主题切换是否正确；图片是否只是“单独好看”而放进页面就失去重点。

根据问题选择调整原图构图、已有图片定位配置或已有布局变体。不要为了保住一张图而限制文章标题长度、截断摘要，或在共享布局中增加按文章 slug 判断的样式。

按当轮范围交付：只看效果就做预览；已要求直接接入则修改对应资源与文章配置，并做实际页面检查。不要因为生成了一张图就顺手改正文、首页列表、主题系统或发布网站。

## 保存与交付

- 保留可追溯的原始图；项目使用的最终资源必须进入项目，不能引用临时目录或生成工具的私有缓存路径。
- 沿用项目资源管线。格式转换或压缩应从原始图做，记录尺寸、格式和前后体积，避免反复有损转码。重生成、调色和格式压缩不是同一件事。
- 日夜图使用同一主体且便于配对的命名。只有明确要求替换时才覆盖当前资源，否则保留独立候选版本。
- 交付图、实际展示证据和简短说明：所选意象、单图／双图、接入位置、验证过的状态。尚未接入或未验证的部分如实说明，不把 mockup 当运行页面。
