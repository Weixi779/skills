# SwiftUI 写法整理

这是用户的个人表达习惯，不是所有 SwiftUI 项目的统一架构。当前请求和项目事实优先。默认保持行为，只整理已授权的范围。

## 先理解用户已经改过的部分

- 读完整目标 View、必要的子视图和调用点；用户提供了改写样例时，先对照实际差异，再解释采用的写法。
- 区分明确偏好、当前组件的选择与自己的推断。不要把“某个子视图内部用 Rectangle”理解为“删除这个子视图”。
- 已明确的本地整理直接实施，不额外增加确认环节。若涉及公开 API、状态归属或交互变化，不能用“整理风格”代替这类改动的授权。

## View 的结构与归属

- 主 `body` 应能看出页面或组件由哪些部分组成。拆出内容时，以是否需要显式入参选择形式：有入参用独立 `struct …: View`；没有入参、只是组织当前视图的局部内容，用 `private var …: some View` 计算属性，不为此单独创建类型。
- 不要为了省去参数，把本来需要显式输入的子视图改成隐式捕获父级数据。反过来，也不要为了抽 struct 凭空制造参数。已有独立状态、任务或复用边界的 View 不因“没有入参”就机械内联。
- 需要独立类型且只服务当前父组件的辅助 View，优先作为父类型内部的 `private struct`，放在主 `body` 后面。多个组件实际共享的实现按需要放到模块内部，不为整齐强行嵌套或重复实现。
- 名字应能表达展示职责，用户接受稍完整的名称。结合现有命名保持一致，不机械删除前缀，也不规定所有嵌套类型都必须重复完整组件名。
- 不为压缩行数拆分每一段 modifier；短小且完整的 View 可以保持原状。无入参的视图片段与派生数据都可以用计算属性清晰表达。
- 相同渲染结构、不同语义入口的简单子视图，可以合并为一个 View，提供有含义的初始化入口。不要仅因都使用同一种基础控件，就合并布局、交互或生命周期不同的视图。

## 初始化整理输入，body 构造视图

- 简单展示组件优先存储数据和配置，在 `body` 中完整构造视图及其 modifier。避免在 `init` 里配置一部分具体 View 再存起来，使读者需要跨两处拼出渲染过程。
- 初始化可处理固定输入，例如资源、文字结构、明确的展示角色。不要为追求“init 整理参数”而缓存全部派生值，或为每种环境预存一份 opacity、color 等字段。
- 随 Environment、主题、状态变化的值，在实际使用处根据当前输入计算。不要在 `init` 中读取尚未安装的环境，也不要把动态主题颜色提前固化。
- 保留解释这些变化所需的语义数据是合理的；不必为了消灭子视图里的所有判断再加一层 Configuration、Resolver 或闭包工厂。
- 这不禁止容器接收泛型 `Content` 或 `@ViewBuilder`。区分真实的内容组合能力与简单控件里无必要地保存具体 View。

## Environment 是共享上下文，不是参数中转站

- 先判断数据的作用范围。整棵子树共享的展示规则适合环境；单个元素的内容、状态、行为通常继续显式传递。不是所有名为 layout 或 style 的值都天然属于环境。
- 一旦已确定某规则由环境统一提供，真正使用它的后代 View 自行读取同一环境。不要只在中间一层读取，再继续通过 init 层层转发。
- 同一规则不要再保留“显式参数优先、环境作为默认”的平行通路。需要改变某个作用域时由其上层设置环境；已有真实的独立覆盖需求应单独设计，不能在风格整理中擅自添加。
- 注入位置和默认值要与实际独立使用场景一致。环境传递属于 SwiftUI 实现，不应把它混入跨技术栈共享的数据模型。
- 不为使用 Environment 自动新增公开 modifier 或公开环境 API；对外入口取决于已确认的组件边界。

## 布局与表达

- 外层负责组成部分之间的关系，子视图负责自身展示。先明确某段空间是子视图内边距，还是两个元素之间的间距，再确定 modifier 放在哪里。
- 有无相邻内容时是否仍需要该空间，是判断归属的有效依据；不要看到 padding 就一律挪进子视图，也不要照抄历史常量作为新契约。
- 分隔线等几何元素优先用 `Rectangle().fill(...)` 等直接表达；这与将它封装为独立 View 不冲突。纯间距优先清楚地表达为 spacing 或 padding，不机械引入透明占位 View。
- 长初始化参数和复杂 modifier 参数按层级展开；短表达保持紧凑，遵循项目 formatter。不要为了排版交换 modifier 顺序，尤其是 frame、padding、background、clip、opacity、contentShape 和 accessibility。

## 不从案例推导通用组件设计

本 skill 不决定组件家族名、UIKit/SwiftUI 的后缀方案、是否使用 Item/Model、是否支持富文本、是否需要 builder、ID 校验、布局数值或呈现入口。这些属于具体 API 和需求。

同样，不把当前内部视图不公开推导为“所有组件必须只有一个 public View”。对已发布的 API，先查消费者并遵守当前授权；不能因为偏好 private 就直接缩小可见性。

## 收尾核对

- 对照用户样例及最终差异，确认没有新增平行配置通路、冗余派生状态或无必要的封装。
- 拆分前后保留 View 身份、状态与任务生命周期、主题更新、点击范围、禁用、选中和无障碍语义；尤其注意把条件、ForEach 或状态移到新边界可能带来的变化。
- 按项目要求执行格式与 lint。纯声明整理做适当编译检查；改变环境读取或更新路径时，验证默认值、继承和动态变化，按需检查实际布局或渲染。
- 保留无关 WIP，不自动提交、安装 skill 或回写个人 Memory。简要报告改动与验证边界，不把编译成功等同于视觉验收。
